# D1 and Jev adapter research

Date: 2026-10-15. Primary-source research only; no model loading or inference.

## Finding

“Open Jev” is a useful analogy, not a model identity. Jev is TypeSafe's model; Liquid's d1 is a separate model family using compatible typed-decision conventions. The common interface describes inputs and outputs, not equal weights, training, accuracy, or Romanian competence. TypeSafe describes System One as state plus narrow questions, returning typed values and probabilities without generated prose. Its three relevant primitives: Choice (named alternative), Score (ordered rubric), Noul (probability of a proposition). Questions are independently evaluated against shared state; combining independent factors belongs in application code. [TypeSafe introduction](https://docs.typesafe.ai/introduction)

Liquid released open-weight d1-3B and experimental d1-omni-600M on **October 7, 2026**. The release describes single-forward-pass decision inference and explains d1-3B's construction from LFM2.5 backbones. The separate hosted d1's results must not be presented as measurements of the downloaded d1-3B quantization. [Liquid release](https://www.liquid.ai/blog/d1-open), [hosted d1 announcement](https://www.liquid.ai/blog/d1-decision-model)

## Romanian evidence and uncertainty

d1-3B's model card lists 3.12B parameters, 32,768-token context, text/JSON/image state, and zero generated output tokens. Its metadata lists 16 languages; **Romanian is absent**. This establishes missing declared coverage, not proof that Romanian always fails. The card supplies general public-benchmark results; it does not establish Romanian Scrabble rarity accuracy. Its reported latency uses specific warm hardware/runtime configurations; it does not predict this machine's LM Studio throughput. [Liquid model card and language metadata](https://huggingface.co/LiquidAI/d1-3B/blob/main/README.md)

Planning consequence: treat Romanian rare-word competence as an unanswered empirical question. Evaluate rare, archaic, regional, technical and inflected allowed spellings separately. Definitions may make an unfamiliar word understandable while saying little about how often a player encounters it. Measure that distinction with held-out human judgments and corpus evidence.

## Serving interface

LM Studio documents **POST `/v1/systemone`** for loaded decision-model identifiers. Request fields: `model`, `state`, `questions` keyed by question identifier; response: `answers` keyed by the same identifiers. Question fields: `type`, `instructions`, and `criteria`. Choice uses an object; Score an ordered array; Noul a binary proposition. This is the closest interface to d1's published schema. [LM Studio System One endpoint](https://lmstudio.ai/docs/developer/jev-compat/systemone)

LM Studio also offers an OpenAI-compatible Decisions format. Its example uses `input`, an array of named questions, and `predicate`, with OpenAI Python 3.26.0 or later. These are distinct wire formats; an adapter must choose one explicitly. Recommendation: start with System One and the project's existing HTTP stack; avoid adding an SDK solely for schema translation. [LM Studio Decisions endpoint](https://lmstudio.ai/docs/developer/openai-compat/decisions)

llama.cpp's documented System One responses expose choice probabilities, score probabilities and expected **zero-based level index**, or a Noul probability. Score supports 2–10 levels. Invalid requests return 400; unsupported model types 501. It documents model-file temperature scaling and explicitly says probabilities need not be calibrated for the caller's data. These are upstream reference semantics; verify the installed LM Studio runtime against recorded fixtures before relying on every detail. [llama.cpp System One API](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-v1systemone-typesafe-compatible-system-one-api)

## Probability handling

TypeSafe confidence summarizes distribution concentration; it is derived from probabilities, not an independent measure of truth. Choice and Score use different formulas. Preserve full distributions and original confidence. Do not equate `confidence=0.9` to 90% Romanian-label accuracy. [TypeSafe confidence](https://docs.typesafe.ai/confidence)

Design alternatives: Score directly expresses an ordered rubric; Choice provides explicit named level keys. The action plan selects Choice with `L1`–`L5` first to make label mapping explicit, retaining Score as a later controlled experiment. With Score, five rubric positions use indices 0–4 and need explicit conversion to pipeline levels 1–5. Preserve per-level probabilities either way. Do not silently round a fractional expectation: two distant probable levels can average into an unsupported middle class.

## Adapter recommendation

1. Separate decision transport from existing chat generation. One text-only word state per request initially; named rarity question, bounded timeout/retries, strict response validation.
2. Put exact authorized Scrabble spelling, normalized lookup spelling and optional dictionary evidence in state. Frequency values computed by code; never ask D1 to invent counts.
3. Save request identity, model/GGUF hash, server/runtime version, rubric version, evidence hashes, probabilities, confidence, latency and failure state as explicit resumable artifacts.
4. Calibration and thresholding downstream of raw inference. Fit only on development/calibration partitions; evaluate once on locked test words/families.
5. Keep Step5's exact-count local-ID contract separate. A per-word decision model does not natively provide compliant exact-count subset selection. First replace Step2 scoring experimentally; design any later deterministic ranking/subset algorithm explicitly and test its contract.
6. Initially offline contract tests, synthetic/recorded response fixtures, preprocessing and evaluation work only. Live verification deferred until RAM is available and loading explicitly authorized. No inference health probe: a request might trigger server loading.

## Open questions requiring measurements

- Bare Romanian spelling vs spelling plus Romanian definition vs bilingual gloss.
- Exact-form frequency vs controlled lemma-family evidence; collision handling for diacritic-free board spelling.
- Whether D1 improves over corpus-only and current-classifier baselines, especially rare-word false-common errors.
- Calibration after quantization, actual per-word throughput and peak memory on the installed runtime.
- Actual served response details, batch/parallel behavior and failure recovery. Documentation compatibility is not an executed integration test.
